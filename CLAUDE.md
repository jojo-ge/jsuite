# jSuite

One local Nuxt app, **jTicket** (`apps/jticket`), plus shared packages, behind
one Caddy edge; OrbStack resolves the `.local` names and terminates HTTPS.
Documents, charts, reviews and the diff viewer were once apps of their own
(jExplain, jChart, jReview, jDiff); they are jTicket features now, and their old
hostnames only redirect into jTicket.
`README.md` covers architecture; this file is for routing requests to the right
jTicket feature, and the rules that keep the checkout consistent. The `jsuite`
skill (installed globally by `./jsuite setup`) carries the same map for sessions
outside this repo.

## Routing — which part of jTicket does a request belong to?

The UI names a project's type, not its mode: a `standard` project reads
**Build** and a `prreview` (PR review) project reads **Review** — so "a build
project" means mode `standard` and "a review project" mode `prreview`. Only
the wording differs (`app/utils/projectType.ts`); the stored modes, the API
and the prompt kinds keep their names. A **Plan** project is mode `plan` — a
map plus research and decision tickets, worked with the `jplan` skill. It was
called wayfinder (mode `wayfinder`, command `/jwayfinder`) before the rename;
the API still reads `"mode": "wayfinder"` as `plan`. A **Plan review** project
is mode `planreview` — a review of one plan's spec and ticket plan before its
builds run.

Everything is driven over jTicket's HTTP API on :43000, through the `jt` CLI
(`bin/jt`, installed to `~/.local/bin/jt` by `./jsuite setup`;
`jt get|post|… PATH [JSON|@file.json|-]` for raw calls).

| Request smells like… | Feature | How to drive it |
| --- | --- | --- |
| tickets, epics, breakdowns, boards, specs, draft docs | the board | skills `to-jticket`, `to-jdoc` (specs and every other doc; it absorbed `to-jspec`), `jplan`, `jimplement` |

PR review projects stay off it (they live on the Reviews board) |

| multi-reviewer code review of a project's branch — several reviewers, dedupe, findings → tickets | **Review** tab + review room | a project's **Review** tab (`POST /api/projects/:id/reviews {branch?, base?, reviewers?}`) dispatches four Opus 5.5 reviewers into herdr (always the global `/code-review` skill), each publishing a report document at a pre-assigned key via `/jreview-report`; the review watcher (`server/plugins/reviewWatcher.ts`) sees every report land and dispatches `/jreview-triage`, which POSTs deduped findings back, then closes the review's herdr panes and removes its worktree. The human picks findings and files them as tickets on THAT project (`POST /api/projects/:id/reviews/:key/tickets`; each finding records its ticket key). Every review belongs to a project — the engine (`server/utils/reviewActions.ts`, routes `/api/reviews/**`) refuses one without. The room is `/reviews/<key>` (`/r/<key>` is an alias): reviewers with re-dispatch/skip/retry, findings with their tickets' status, the reports, live over `GET /api/reviews/:key/watch`, and **Forget** (`DELETE /api/reviews/:key`: the record and its worktree go, tickets and reports stay; not offered while a consensus or agreement review is in flight). A review with no live project shows on no Review tab: the Reviews board lists those under **Reviews without a project** (`GET /api/reviews?orphaned=1`), and the room of a triaged review that predates projects has a project picker that files its findings into the chosen project (`projectOrHomelessReview` in `server/utils/jreview.ts`). State in `.data/jreview/` |
| review someone's GitHub PR with several reviewers — "set up a review of PR 123", "jreview this PR", post the findings to the PR | **Reviews** board + PR review projects | the **Reviews** board (`/reviews`, `app/pages/reviews/index.vue`) lists PR review projects (they leave the projects board and Today; one in a graph also appears there, as a Review node) and, under **Open PRs**, the codebase's open GitHub PRs, 25 at a time with **Load more** (`GET /api/repos/prs?repo=` — one GitHub search: drafts left out unless `&drafts=1`, `&mine=1`, `&reviewing=me|team`, `&cursor=` for the next page; the author chips narrow what is loaded); **Make review project** makes the PR's project and opens its Review tab (**Open review project** when it has one) — it dispatches nothing: the human presses **Start review** there. The create modal's **Review** type makes one with no PR yet (`POST /api/projects {mode: "prreview", repo}` — the repo is required, the title optional): until a PR is picked its page is only the PR picker (`OpenPrList` with `attachTo`; `reviewNeedsPr` in `app/utils/prReview.ts`), and picking one is `POST /api/projects/:id/pr-review {pr}` — the head is fetched onto `jreview/pr-<n>` and attached, nothing is started (409 once the project has its PR, or when another project already reviews that one). The project's **Review** tab's **Start review** (`POST /api/projects/:id/reviews {reviewers?}` — 2–4, default 3, Opus 5.5 high; `startPrReview` in `server/utils/prReview.ts`; 409 while one is still out) re-fetches the PR head and starts ONE **agreement review** of the PR's diff (`agreement: {loop}`, `project`, `pr`, `verify: true`): reviewers use the codebase's own review skill when it carries one, an Opus 5.5 `/jreview-consensus` keeps only what every reviewer raised, adversarially verifies each, judges approvability and hands findings + `assessment` back (`POST /api/reviews/:key/findings`); jTicket files each finding as a record-only HITL `bug` ticket on the project (labelled `review:finding`, never frontier, never dispatchable; a rerun updates the matching open ticket instead of filing a duplicate). The Review tab shows the verdict and the consensus session's summary (which prefills the post), **Rerun review** (the same `POST …/reviews`: re-fetch the head, review again) and **Post to PR** (`POST /api/projects/:id/reviews/:key/pr-comments {ticketKeys, body}` → one GitHub review with the human's gh auth, event COMMENT always — nothing ever approves or requests changes; "posted" is stamped on each ticket). Nothing on a PR review project is ever dispatched: a ticket the human adds by hand is a record too (`isRecordOnly` in `app/utils/reviewFindings.ts`), and the review neither runs nor reads it |
| a few small tasks or decision tickets in ONE session — "run these together", "one agent for all of these" (not the orchestrator) | the board | tick two or more frontier cards on the board and press **One session** (beside Run selected): one claude session in its own `PROJ-n · batch · …` tab works them one after another in key order, each on its own resolved hand-off (`POST /api/projects/:id/herdr-batch {prompt, tickets}`; wrapper prompt kind `batch`, overridable per project/codebase/global; logic `resolveBatchPrompt` in `app/utils/prompts.ts`, dispatch `dispatchBatchSession` in `server/utils/herdrDispatch.ts`). No claims, no budget, no subagents; HITL tickets ask in that pane; refused (409) under auto mode unless every ticket is HITL |
| read a diff — a project's integration branch, a local PR, a GitHub PR, two refs; a guided tour of the change | **Diff** tab | the project's **Diff** tab (`app/components/ProjectDiff.vue`; `GET /api/projects/:id/diff` with no target = the integration branch vs its base — the default branch, or for a stacked build the slice base, so it shows only its own work (the target's `baseLabel` names the upstream branch) — (a PR review project's `jreview/pr-<n>` vs its base), `?pr=PR-n`, `?gh=<n>`, `?head=&base=`; one file at `…/diff/file`; the file list's kind chips — source, tests, docs, config, generated, assets — narrow the files shown and its order menu sorts them by path or line churn, `app/utils/diffFiles.ts`; links are `/projects/KEY?tab=diff&…`, built by `diffTabUrl` in `app/utils/diffTarget.ts`). **Build tour** (`POST /api/projects/:id/diff/tour` with the target; `DELETE` cancels) dispatches one Opus `/jdiff-tour` session that posts the tour back (`…/diff/tour/artifact`, then `…/complete`); tours are for humans only, never handed to reviewers. A tour records the head commit it was written against (`headOid`), and the tab warns when the diff's head has moved since (`tourIsStale` in `app/utils/tour.ts`). Tours live in `.data/jdiff/tours.json` |
| a project's integration branch — cut or set it, stack a build on another, sync from upstream, connect a worktree, open the roll-up PR | **Overview** + **Pull requests** tabs | the Overview tab's integration-branch card (`app/components/ProjectIntegrationBranch.vue`: cut/set via `POST /api/projects/:id/integration-branch {branch?, base?}`, the existing-branch picker `GET …/branches`, **Connect worktree**); the roll-up PR (push, then open or find the integration → base PR) is on the Pull requests tab (`POST /api/projects/:id/integration-pr`). **Stacking**: `project.integrationBase` is the branch a build's integration branch was cut from and its roll-up PR targets — `''` = the default branch, or another build's integration branch (picked on the card when cutting, set by Move on's `stackOn`, or `PATCH /api/projects/:id {integrationBase}`); a build stacks on at most one upstream, and a stacked build shows only its own work — Diff tab, slice size, Review tab — measured from the **slice base**, where its branch meets the upstream's (`server/utils/integrationBase.ts`; decisions `app/utils/stacking.ts`). `GET /api/projects/:id/integration-branch` is the branch against its base (base, ahead/behind, unpushed, whether the base still exists and the upstream looks merged, what Sync would do, `slice: {files, additions, deletions}`; `?force=1` re-asks origin and gh). **Sync from upstream** (`POST …/integration-branch/sync`) fetches, then MERGES into the branch locally — never a rebase (ticket branches hang off it), never a push: upstream still open → its branch; upstream squash-merged → what it merged into (usually the default branch), which becomes the base, and the open roll-up PR is retargeted there; not stacked → the default branch. A conflict, or a dirty worktree holding the branch, answers `ok: false` with nothing moved. Nothing in jTicket pushes or pulls the integration branch otherwise |
| run a project hands-off — implement → merge → review → fix loops | **jButton** (auto mode) | the project's **jButton** (auto mode, confirm modal; `POST /api/projects/:id/auto`) — `server/plugins/autoLoop.ts` dispatches the AFK frontier on Opus 5.5 (`/jimplement`, local PRs) — or, in **orchestrated** mode (picked in the confirm modal, kept on `project.auto.orchestration`), one Fable 5.2 `/jorchestrate` session per phase that runs the tickets through Opus 5.5 subagents in pooled worktrees, claiming each via `POST /api/projects/:id/auto/claim` (the server refuses claims past the budget, 2–4 in flight — never 1, and a phase with fewer than 4 tickets runs them as plain sessions instead: an orchestrator with nothing to run side by side costs more than the work) and spec-checking it against its acceptance criteria before marking it done; the watchdog then watches the orchestrator and replaces it if it stalls — then waits for every ticket (finished with no PR yet → looks twice more, 20s apart, before skipping the merge), runs the merge sweep on Sonnet 5 and waits for it to report back (`POST /api/projects/:id/auto/merge-report`; a PR it couldn't land pauses the loop), starts a 2-reviewer consensus review of the loop's diff (`reviewers: 2, consensus: {projectKey, loop}`; its Sonnet 5 `/jreview-consensus` session files only findings BOTH reviewers raised — in-scope ones (or any critical break) as tickets in the project, out-of-scope ones into a separate `<PROJ-key> follow ups` project so the run stays on task; reviewers mark `scope: in|out` per finding), implements + merges those, then starts the next loop. HITL tickets are never auto-dispatched. A watchdog keeps loop-dispatched tickets from hanging: a session stopped with its ticket open for 5m is prompted to finish; still stopped 10m later (or its session gone 1m) the loop marks the ticket done itself and files the rest as an `auto-loop:carryover` ticket that inherits its blocks (a second carryover is HITL). "Stop at the end of next loop" finishes the loop in progress, then turns auto off. The board's **Loop frontier / Loop selected** button (beside Run all / Run selected) runs exactly one loop — over the whole AFK frontier, or only the ticked AFK tickets — then auto turns off (`{enabled: true, once: true, tickets?: [keys]}`). After every phase-ending step the loop closes the herdr panes it's finished with — done tickets' panes, its merge/report panes; never a working/blocked agent, an open ticket's pane, or an unlabelled pane (`panesToClean`; a review's tabs are the review watcher's to close). With no open ticket left, a last Opus 5.5 session writes the project's ≤500-word **outcome report** (its `outcome`-labelled doc) and reports back (`POST /api/projects/:id/auto/outcome-report`) before auto turns off. State: `project.auto` |
| run a hand-built sequence — pick which tickets go together, who runs each, and where merges, reviews and gates happen | **Run setup** tab | the project's **Run setup** tab shows the **run plan**'s steps as a board, or as a **graph** (`RunPlanGraph.vue`, layout `app/utils/runPlanGraph.ts`: a band per step, a card per ticket, orchestrator boxes, review brackets showing what each review reads, blocker arrows, slice-report markers; the Board/Graph toggle is remembered per browser) (`project.runPlan`, saved via `PUT /api/projects/:id/run-plan`; logic `app/utils/runPlan.ts`); every edit is a modal — adding an **implement** step is a 3-step wizard (pick tickets → who runs each → confirm). An implement step's tickets each run as **their own agent** (one `/jimplement` session, `--model`/`--effort` from the step's `dispatch` — Opus 5.5 high by default — or the ticket's own `runners[key]`) unless put in an orchestrator group (`step.groups`): then a Fable 5.2 `/jorchestrate` session works that group through subagents on the step's model/effort — or the group's own (`step.groupRunners`, one per group: cheap subagents for a box of small tickets beside a box of heavy ones) — under its own budget (`GET …/auto/queue?orchestrator=n` marks solo tickets `solo`; claims carry `orchestrator`, a solo ticket's is refused). Solo agents and orchestrators run side by side (`orchestratedKeys` / `runnerFor`; `effectiveOrchestration()` is what the engine, server and strip read). HITL tickets are waited on, never dispatched. **merge** sweeps the plan's open PRs. **review** (from a checkpoint — plan start, the previous review, or any earlier step): optionally an **architectural & technical reviewer first** (`step.review.arch`; review `pass: 'architecture'`, one reviewer on the global `/jarch-review` skill; the consensus session files its `architecture` findings as mandatory fix tickets and `technical` ones as advisory HITL tickets) — phases `arch-reviewing` → `arch-fixing` → `arch-merging` — then the regular 2–4 reviewer consensus review (`step.review.model`/`effort`, Opus 5.5 medium by default; the review gets `context.review` = the arch review so its reviewers read that report first) whose agreed findings are fixed and merged inside the step. **gate** waits for Continue. Before every implement step after the plan's first, when the tip moved since the last one, the engine enters `slice-reporting`: one Opus 5.5 medium `/jslice-report` session writes a facts-only ≤300-word `slice`-labelled doc (`server/utils/sliceReport.ts`; reports back via `POST …/auto/slice-report`), and every hand-off, claim prompt and review of that step opens with "read DOC-n first" (`auto.lastSliceDoc`; recorded on the step as `sliceDoc`); the outcome report synthesises the slice docs. Strict ordering: a ticket's open blockers must sit in an earlier implement step with a merge between. **Start plan** (`POST /api/projects/:id/auto {enabled: true, plan: true}`; 409 when auto is already on or a build is in progress) runs it on the jButton's engine (same watchdog, orchestration, merge reports, pane cleanup); `{continue: true}` passes a gate. A running plan is **locked whole** (`PUT …/run-plan` → 409): the tab's **Unlock & stop** turns auto off, the strip's **Stop after this step** finishes the step first. Either leaves `project.auto.resume` (where the run got to), and the tab's **Continue plan** (`{enabled: true, plan: true, resume: true}`) picks the saved plan up at that step — finished steps stay done (matched by id and content, so later edits are allowed for; `resumePlanRun` in `app/utils/autoLoop.ts`), checkpoints and slice doc carry over, and only the steps from there on are validated; **Start from the top** is the other button. A finished ticket in an implement step is never a validation problem: the engine skips it. **Build with Fable** (`POST /api/projects/:id/run-plan/build`, `DELETE` cancels) dispatches one Fable 5.2 high `/jrunplan` session (the `runplan:build` prompt kind — overridable per project/codebase) that reads the project, docs, open tickets and code, weighs each ticket, chooses who runs what on which model/effort under the **step concurrency rule** (`STEP_SESSIONS_MAX` in `app/utils/runPlan.ts`: at most 4 sessions at once in a step, an orchestrator counting as one — own agents only (4 at once), mixed (1 orchestrator + 3 own agents at once), or 2 orchestrators alone; each orchestrator 2 in flight — never 1 (`BUDGET_MIN`) — and 4+ tickets in its group (`GROUP_MIN`; fewer is a validator problem, and a group that has shrunk under it by step time runs as own agents, `liveGroups`); groups folded to 2 and budget clamped on save, a solo ticket beside two orchestrators a validator problem; a review's fix tickets go out 3 at a time (`FIX_SESSIONS_MAX`); a merge sweep, review or report silent past `JOB_STALL_MS`/`REVIEW_STALL_MS` pauses the run (`phaseStall`, Retry step re-runs it); turning a run off closes its orchestrator panes) and **the step's ticket list is a queue** the builder orders — the engine (`soloQueue`) starts the next own-agent ticket as a session frees, the board/graph/strip show the queue — places merges/reviews/gates sparingly (reviews for drift and breakage, scaled to the project, always one at the end; HITL tickets in their own step + gate or left out), records a **prediction** for every open ticket it places (`step.predictions[key]` = `{weight: light|medium|heavy, minutes, risk, why}`, `TicketPrediction` in `app/utils/runPlan.ts` — minutes grounded in the codebase's measured medians; the engine never reads it, the harness capture scores it against the run), PUTs the plan until `problems` is `[]` and reports back (`POST …/run-plan/built` — 400 while an open implement-step ticket has no prediction; a plan built by hand needs none); `project.runPlanBuild` marks it in progress and the tab is read-only meanwhile. State: `project.auto.plan` / `cursor` / `planLog` / `checkpoints` |
| cut a large piece of work into reviewable slices and hand it along — plan → builds → reviews; how projects lead into each other and what each delivered; "move on" to the next project | **Graphs** | the **Graphs** menu (`/graphs`: a card per graph — its type chain, progress, where it is now) and each graph's page (`/graphs/G-n`; `?node=<nodeId>` opens a node's briefing; the old `/graphs?g=G-n` redirects there). A **graph** is stored and hand-built: nodes — plan, build and review projects, any mix, a project in at most one node of one graph — joined by directed, acyclic edges ("work passes from this project to that one"); a node may be **proposed** (a mode and title, no project yet; its `note` says why it exists). A build whose integration branch other builds use too (`branchSharers`) has no slice of its own: the drawing, the list and the briefing say the branch is shared with those projects (by key) instead of showing the branch's size as this build's. A graph's first project (nothing before it) shows no Move on banner, and the plan a ticket plan's graph is made around counts as moved on into. Logic `app/utils/graphs.ts`, server `server/utils/graphs.ts`, UI `GraphCanvas.vue` + `GraphBriefing.vue`. Machine-local (never synced); cross-project ticket blockers are plain ticket facts and make no graph |
| turn a finished plan into build tickets — the spec, the tickets, which builds and reviews to make | **Ticket plan** tab (Plan projects) | a Plan project's **Ticket plan** tab (`ProjectTicketPlan.vue`): **Draft ticket plan** (`POST /api/projects/:id/ticket-plan/build`, `DELETE` cancels; prompt kind `ticketplan:build`, overridable; Fable 5.2 high, `JTICKET_TICKETPLAN_MODEL`/`_EFFORT`) dispatches one session on skill `jplan-to-jtickets` (button-only) that reads the plan's map, resolutions, docs and the code, writes the spec as a doc on the plan (`to-jdoc`), drafts the build tickets on the plan, and **proposes** the graph's shape — it get-or-creates the plan's graph (`POST …/ticket-plan/graph`) and adds proposed nodes: builds sized so each roll-up PR is reviewable in one sitting (a large one split into stacked builds; each node's `note` says what the slice is and roughly how big), a Review after every non-trivial build, and a Plan review before the builds when the plan is large or risky — then reports back (`POST …/ticket-plan/built {summary?}`); `project.ticketPlanBuild` marks it in progress. ## Rules of the suite

- **jTicket is the only app.** New product surface goes into `apps/jticket`, not
  a new app. `apps/jticket/tests/suiteWiring.test.ts` guards it: `apps/` and the
  `APPS` table in `./jsuite` hold only jTicket, and the lockfile has no other
  app importer.
- **State lives in `.data/<area>/` at this root, never inside an app.** Use
  `@jsuite/data` (`appDataDir`/`appDataFile`) to resolve paths. The directories
  keep the retired apps' names: `.data/jticket/` (the store — API-only: go
  through :43000, don't hand-edit `jticket.json`), `.data/jexplain/` (the
  document pool), `.data/jchart/` (the chart pool), `.data/jreview/` (review
  records), `.data/jdiff/` (tours).
- **Ids are UUIDv7s; keys are for people.** Every entity's `id` is a bare,
  time-ordered UUIDv7 (`newId`, `server/utils/ids.ts`); its key (`TICK-n`,
  `PROJ-n`, `G-n`) is what people, links and prompts use. Resolve a reference
  with `findByRef` (id, key or legacy id), never `x.id === ref`. The pre-UUID
  ids (`tick_…`) were rewritten once across `.data` by
  `POST /api/admin/migrate-ids {dryRun?}` (409 while auto mode or a run-plan
  build is on; a second run is a no-op): it copied `.data` to
  `.data.backup-ids-<stamp>` beside it first (to undo: stop jTicket, swap the
  copy in, start) and keeps old → new in `.data/jticket/id-migration.json`,
  through which a legacy id still resolves. Shares made before it must be
  re-made.
- **URLs always carry the scheme**: `https://jticket.local`. The bare host port
  (:43000) works too, but the `.local` name is what tooling hardcodes. The port
  is fixed: the `APPS` table in `./jsuite`, the `Caddyfile` and skills that
  hardcode it (`to-jticket` → :43000) must stay in sync.
- **The edge's hostnames are one set.** `DOMAINS` in `./jsuite`, the
  `dev.orbstack.domains` label in `docker-compose.yml` and the `Caddyfile`
  hosts must match (`suiteWiring.test.ts`). `jsuite.local` is the static page in
  `www/`, `jticket.local` is the app, and `jexplain.local`, `jreview.local` and
  `jchart.local` are **redirect-only**, because stored tickets, docs and review
  reports still link to them: `jexplain.local/e/K` → `/e/K`, `jreview.local/r/K`
  → `/reviews/K`, `jchart.local/c/K` → `/charts/K` (302s, query kept; any other
  path lands on that feature's index). Never route a new link through them.
- **Skills are owned by jTicket** in `apps/jticket/.claude/skills`; the
  suite-level `jsuite` skill lives in `.claude/skills/` here at the root.
  `./jsuite setup` installs all of them globally from `SKILLS_MANIFEST` in
  `./jsuite`, and prunes links that point nowhere — a new skill goes in the
  manifest's `apps/jticket` row, the only list. `apps/jticket/j-setup` has no
  list or link logic of its own: it runs `./jsuite skills --only apps/jticket`,
  so `link_skills` in `./jsuite` is the one implementation
  (`suiteWiring.test.ts` runs both against a throwaway config dir).
- **One git repo covers the whole workspace.** Commit everything (the app,
  packages, skills, `www/`) from this root.
- **Don't restart jTicket blindly.** `./jsuite status` first; `./jsuite start` is
  idempotent when it's already running but refuses a port held by a process it
  didn't start. The log is `logs/jticket.log` (`./jsuite logs jticket`).
- **From a worktree, run jTicket only as a sandbox.** The live suite runs from
  the main checkout, and live projects are mid-run. In a worktree, never run
  `./jsuite start|stop|restart|setup` (setup repoints the global skill links
  at the worktree) and never touch the Caddyfile or OrbStack. To see a change
  in the running app, use `./jsuite sandbox`:
  - It runs jTicket in the foreground from this checkout on the first free
    port from 43100, over a copy of the live `.data` in `.sandbox/data`.
    `--fresh` takes a new copy.
  - Engines are off: no auto loop, review runner or share sync. `--engines`
    turns them on.
  - git/gh writes are refused, and so are herdr sessions, except inside the
    throwaway repos you pass with `--repos /abs/a:/abs/b`.
  - Sessions it starts go into herdr session `jsuite-sandbox`, never the live
    one. Someone has to run `herdr session attach jsuite-sandbox` in a
    terminal first.
  - Those sessions are pointed back at the sandbox: their prompts are
    rewritten, and `JTICKET_URL` is set for their commands.

  The rules live in `apps/jticket/server/utils/sandbox.ts` and
  `sandboxRules.ts`. A sandbox session still reads the globally installed
  skills (the live versions), so skill edits on a branch aren't exercised
  until it merges.

## Layout

```
jsuite            # launcher: start/stop/restart/status/logs/open/setup/sandbox/root
                  # (setup also installs every jskill globally — SKILLS_MANIFEST)
Caddyfile         # edge config — jticket.local, jsuite.local, and the redirect-only hosts
www/              # static page at https://jsuite.local
.claude/skills/   # suite-level skills (jsuite)
apps/jticket/     # the app — and every skill but jsuite (apps/jticket/.claude/skills)
packages/         # @jsuite/charting + @jsuite/documents (Nuxt layers), @jsuite/data (.data resolver), @jsuite/herdr (herdr dispatch adapter), @jsuite/relay (sync setup wizard + local broadcast relay)
.data/<area>/     # ALL state, gitignored
bin/jt            # the jTicket CLI
```
