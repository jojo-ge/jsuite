# jSuite

Eight local Nuxt apps (jticket, jdiff, jchart, jexplain, jgrilling, jcode, jmap, jreview)
+ shared packages behind one Caddy edge; OrbStack resolves the `.local` names
and terminates HTTPS.
`README.md` covers architecture; this file is for routing requests to the right
app, and the rules that keep the suite consistent. The `jsuite` skill (installed
globally by `./jsuite setup`) carries the same map for sessions outside this repo.

## Routing — which app does a request belong to?

| Request smells like… | App | How to drive it |
| --- | --- | --- |
| tickets, epics, breakdowns, boards, specs, draft docs | `apps/jticket` | HTTP API on :43000, which skills drive through the `jt` CLI (`bin/jt`, installed to `~/.local/bin/jt` by `./jsuite setup`; `jt get|post|… PATH [JSON|@file.json|-]` for raw calls) — skills `to-jticket`, `to-jspec`, `to-jdoc`, `jwayfinder`, `jimplement` |
| what needs me today — HITL tickets waiting, PRs asking for my review, my PRs' CI, what's building, the TODO inbox | `apps/jticket` | the **Today** page (`/today`, `app/pages/today.vue`): `GET /api/today/github?repo=` rolls up my open PRs' CI and review requests via `gh`; the TODO inbox is the codebase's todo-mode project (`POST /api/projects/todo {repo}`, get-or-create — `/idea` and `/bug` land there) |
| PR review, branch diff, review comments | `apps/jdiff` | `jdiff` CLI (`jdiff pr N`, `jdiff branch B`, `--print`) |
| diagrams the human edits/annotates | `apps/jchart` | skill `j-chart`; API on :43003; state in `.data/jchart/` |
| explainers, walkthroughs, post-mortems, articles | `apps/jexplain` | skill `j-explain` (`explain.py` publish script) |
| grill/stress-test a plan | terminal | skill `grilling` — the default; one question escalates to `apps/jgrilling` only when the operator asks (skill `j-grilling`; API on :43005; state in `.data/jgrilling/`). jGrilling's **Up next** strip (`GET /api/upnext`) lists the HITL grilling frontier from jTicket by project; `POST /api/upnext/:id/start` dispatches that ticket into herdr through jTicket's `POST /api/tickets/:id/herdr`, in its own tab, told to run `/grilling` in the terminal |
| map a codebase — domains, dependency map, walkthrough docs | `apps/jmap` | skill `j-map` (front door); the work runs as a jMap-mode jTicket project (herdr-dispatched `/jmap-scope`, `/jmap-domain`, `/jmap-synthesize` tickets); jMap API on :43007 renders the posted graph; state in `.data/jmap/` |
| build a feature and hand-code its core as a problem — "with jcode", "pose the core as a problem" | `apps/jcode` | skill `jcode` (build and ship as usual, then publish the core piece as a pure-function kata to :43006: a sandbox in `.data/jcode/sandbox/<key>/` with stub + cases + the app's runner, answer hidden); the page's Mark-it button dispatches `jcode-mark` into herdr, which runs the cases, judges, or posts a verdict that unlocks the next hint. Disclosure is server-side: brief → hints → answer. Nothing ships from a kata |
| multi-reviewer code review — several reviewers, dedupe, findings → tickets | `apps/jreview` | the New review button on :43008 dispatches four Opus 5.5 reviewers into herdr (always the global `/code-review` skill), each publishing a jExplain report at a pre-assigned doc key via `/jreview-report`; the server-side watcher (`server/plugins/reviewWatcher.ts`) sees every report land and dispatches `/jreview-triage`, which POSTs deduped findings back — that opens the review in the browser and the watcher closes the review's herdr panes (the jButton's sweep closes the same tabs as a backstop); the human's button splits them into a new jTicket project. A jTicket project's **Review** tab starts the same flow for one of its branches (`POST :43000/api/projects/:id/reviews` → jReview with `project: KEY`) and adds the picked findings to THAT project (each finding records its ticket key). State in `.data/jreview/` |
| review someone's GitHub PR with several reviewers sized to it — "set up a review of PR 123", "jreview this PR", post the findings to the PR | `apps/jticket` + `apps/jreview` | skill `make-jreview-project N` (run in the repo) → `POST /api/projects/pr-review {repo, pr, assess: true}` makes a **PR review project** (mode `prreview`; the PR head fetched onto the never-pushed local branch `jreview/pr-<n>`) and dispatches one Fable 5.2 `/jreview-assess` (prompt kind `prreview:assess`) that picks 2–4 reviewers, writes ONE brief every reviewer reads (a `review:brief` doc), adds `pr:check` tickets only where running beats reading, PUTs the **review plan** (`PUT /api/projects/:id/review-plan`; checks → gate? → one review step) and reports back (`POST …/pr-review/assessed`). The review plan is its OWN run setup — the project's **Review setup** tab, logic `app/utils/reviewPlan.ts`, runner `server/utils/reviewRun.ts` + `server/plugins/reviewRun.ts` — never the Run setup tab, auto mode or `/jrunplan`, which are unchanged. Checks run as `/jpr-check` sessions (read-only, throwaway worktree, verdict on the ticket); the review is a jReview **agreement review** (`agreement: {loop}`, `project`, `pr`, `verify: true`, `context: {brief, checks}`): reviewers use the codebase's own review skill when it carries one, an Opus 5.5 `/jreview-consensus` keeps only what every reviewer raised, adversarially verifies each, judges approvability and POSTs findings + `assessment` back — never tickets. The Review tab shows the verdict, **Rerun review** (`POST …/review-run {action: rerun}`: re-fetch the head, reopen checks) and **Post to PR** (`POST …/reviews/:key/pr-comments` → jReview → one GitHub review with the human's gh auth, event COMMENT always — nothing ever approves or requests changes) |
| a few small tasks or decision tickets in ONE session — "run these together", "one agent for all of these" (not the orchestrator) | `apps/jticket` | tick two or more frontier cards on the board and press **One session** (beside Run selected): one claude session in its own `PROJ-n · batch · …` tab works them one after another in key order, each on its own resolved hand-off (`POST /api/projects/:id/herdr-batch {prompt, tickets}`; wrapper prompt kind `batch`, overridable per project/codebase/global; logic `resolveBatchPrompt` in `app/utils/prompts.ts`, dispatch `dispatchBatchSession` in `server/utils/herdrDispatch.ts`). No claims, no budget, no subagents; HITL tickets ask in that pane; refused (409) under auto mode unless every ticket is HITL |
| a project's integration branch — where it stands vs origin/default, push, fast-forward pull, roll-up PR | `apps/jticket` | the project's **Branches** tab (`GET /api/projects/:id/branch-status?fetch=1`, `POST …/sync` pushes, `POST …/branch-pull` fast-forwards — never merges); logic `server/utils/branchStatus.ts` |
| run a project hands-off — implement → merge → review → fix loops | `apps/jticket` | the project's **jButton** (auto mode, confirm modal; `POST /api/projects/:id/auto`) — `server/plugins/autoLoop.ts` dispatches the AFK frontier on Opus 5.5 (`/jimplement`, local PRs) — or, in **orchestrated** mode (picked in the confirm modal, kept on `project.auto.orchestration`), one Fable 5.2 `/jorchestrate` session per phase that runs the tickets through Opus 5.5 subagents in pooled worktrees, claiming each via `POST /api/projects/:id/auto/claim` (the server refuses claims past the budget, 2–4 in flight — never 1, and a phase with fewer than 4 tickets runs them as plain sessions instead: an orchestrator with nothing to run side by side costs more than the work) and spec-checking it against its acceptance criteria before marking it done; the watchdog then watches the orchestrator and replaces it if it stalls — then waits for every ticket (finished with no PR yet → looks twice more, 20s apart, before skipping the merge), runs the merge sweep on Sonnet 5 and waits for it to report back (`POST /api/projects/:id/auto/merge-report`; a PR it couldn't land pauses the loop), asks jReview for a 2-reviewer consensus review of the loop's diff (`reviewers: 2, consensus: {projectKey, loop}`; its Sonnet 5 `/jreview-consensus` session files only findings BOTH reviewers raised — in-scope ones (or any critical break) as tickets in the project, out-of-scope ones into a separate `<PROJ-key> follow ups` project so the run stays on task; reviewers mark `scope: in|out` per finding), implements + merges those, then starts the next loop. HITL tickets are never auto-dispatched. A watchdog keeps loop-dispatched tickets from hanging: a session stopped with its ticket open for 5m is prompted to finish; still stopped 10m later (or its session gone 1m) the loop marks the ticket done itself and files the rest as an `auto-loop:carryover` ticket that inherits its blocks (a second carryover is HITL). "Stop at the end of next loop" finishes the loop in progress, then turns auto off. The board's **Loop frontier / Loop selected** button (beside Run all / Run selected) runs exactly one loop — over the whole AFK frontier, or only the ticked AFK tickets — then auto turns off (`{enabled: true, once: true, tickets?: [keys]}`). After every phase-ending step the loop closes the herdr panes it's finished with — done tickets' panes, its merge/report panes, past reviews' jReview tabs; never a working/blocked agent, an open ticket's pane, or an unlabelled pane (`panesToClean`). With no open ticket left, a last Opus 5.5 session writes the project's ≤500-word **outcome report** (its `outcome`-labelled doc) and reports back (`POST /api/projects/:id/auto/outcome-report`) before auto turns off. State: `project.auto` |
| run a hand-built sequence — pick which tickets go together, who runs each, and where merges, reviews and gates happen | `apps/jticket` | the project's **Run setup** tab shows the **run plan**'s steps as a board, or as a **graph** (`RunPlanGraph.vue`, layout `app/utils/runPlanGraph.ts`: a band per step, a card per ticket, orchestrator boxes, review brackets showing what each review reads, blocker arrows, slice-report markers; the Board/Graph toggle is remembered per browser) (`project.runPlan`, saved via `PUT /api/projects/:id/run-plan`; logic `app/utils/runPlan.ts`); every edit is a modal — adding an **implement** step is a 3-step wizard (pick tickets → who runs each → confirm). An implement step's tickets each run as **their own agent** (one `/jimplement` session, `--model`/`--effort` from the step's `dispatch` — Opus 5.5 high by default — or the ticket's own `runners[key]`) unless put in an orchestrator group (`step.groups`): then a Fable 5.2 `/jorchestrate` session works that group through subagents on the step's model/effort — or the group's own (`step.groupRunners`, one per group: cheap subagents for a box of small tickets beside a box of heavy ones) — under its own budget (`GET …/auto/queue?orchestrator=n` marks solo tickets `solo`; claims carry `orchestrator`, a solo ticket's is refused). Solo agents and orchestrators run side by side (`orchestratedKeys` / `runnerFor`; `effectiveOrchestration()` is what the engine, server and strip read). HITL tickets are waited on, never dispatched. **merge** sweeps the plan's open PRs. **review** (from a checkpoint — plan start, the previous review, or any earlier step): optionally an **architectural & technical reviewer first** (`step.review.arch`; jReview `pass: 'architecture'`, one reviewer on the global `/jarch-review` skill; the consensus session files its `architecture` findings as mandatory fix tickets and `technical` ones as advisory HITL tickets) — phases `arch-reviewing` → `arch-fixing` → `arch-merging` — then the regular 2–4 reviewer consensus review (`step.review.model`/`effort`, Opus 5.5 medium by default; jReview gets `context.review` = the arch review so its reviewers read that report first) whose agreed findings are fixed and merged inside the step. **gate** waits for Continue. Before every implement step after the plan's first, when the tip moved since the last one, the engine enters `slice-reporting`: one Opus 5.5 medium `/jslice-report` session writes a facts-only ≤300-word `slice`-labelled doc (`server/utils/sliceReport.ts`; reports back via `POST …/auto/slice-report`), and every hand-off, claim prompt and review of that step opens with "read DOC-n first" (`auto.lastSliceDoc`; recorded on the step as `sliceDoc`); the outcome report synthesises the slice docs. Strict ordering: a ticket's open blockers must sit in an earlier implement step with a merge between. **Start plan** (`POST /api/projects/:id/auto {enabled: true, plan: true}`; 409 when auto is already on or a build is in progress) runs it on the jButton's engine (same watchdog, orchestration, merge reports, pane cleanup); `{continue: true}` passes a gate. A running plan is **locked whole** (`PUT …/run-plan` → 409): the tab's **Unlock & stop** turns auto off, the strip's **Stop after this step** finishes the step first. Either leaves `project.auto.resume` (where the run got to), and the tab's **Continue plan** (`{enabled: true, plan: true, resume: true}`) picks the saved plan up at that step — finished steps stay done (matched by id and content, so later edits are allowed for; `resumePlanRun` in `app/utils/autoLoop.ts`), checkpoints and slice doc carry over, and only the steps from there on are validated; **Start from the top** is the other button. A finished ticket in an implement step is never a validation problem: the engine skips it. **Build with Fable** (`POST /api/projects/:id/run-plan/build`, `DELETE` cancels) dispatches one Fable 5.2 high `/jrunplan` session (the `runplan:build` prompt kind — overridable per project/codebase) that reads the project, docs, open tickets and code, weighs each ticket, chooses who runs what on which model/effort under the **step concurrency rule** (`STEP_SESSIONS_MAX` in `app/utils/runPlan.ts`: at most 4 sessions at once in a step, an orchestrator counting as one — own agents only (4 at once), mixed (1 orchestrator + 3 own agents at once), or 2 orchestrators alone; each orchestrator 2 in flight — never 1 (`BUDGET_MIN`) — and 4+ tickets in its group (`GROUP_MIN`; fewer is a validator problem, and a group that has shrunk under it by step time runs as own agents, `liveGroups`); groups folded to 2 and budget clamped on save, a solo ticket beside two orchestrators a validator problem; a review's fix tickets go out 3 at a time (`FIX_SESSIONS_MAX`); a merge sweep, review or report silent past `JOB_STALL_MS`/`REVIEW_STALL_MS` pauses the run (`phaseStall`, Retry step re-runs it); turning a run off closes its orchestrator panes) and **the step's ticket list is a queue** the builder orders — the engine (`soloQueue`) starts the next own-agent ticket as a session frees, the board/graph/strip show the queue — places merges/reviews/gates sparingly (reviews for drift and breakage, scaled to the project, always one at the end; HITL tickets in their own step + gate or left out), PUTs the plan until `problems` is `[]` and reports back (`POST …/run-plan/built`); `project.runPlanBuild` marks it in progress and the tab is read-only meanwhile. State: `project.auto.plan` / `cursor` / `planLog` / `checkpoints` |
| see how projects lead into each other, and what each delivered | `apps/jticket` | the **Graphs** page (`/graphs`) — a ticket blocked by a ticket in another project links the two (no graph entity); each connected group is a graph named "first → last", drawn with each project's status and its outcome report. Display only — projects are kicked off by hand. Each graph's id is `G-<KEY>` (its earliest project's key); resolve one named in conversation with `GET /api/graphs/G-KEY` (a member project key works too), list with `GET /api/graphs`. Logic: `app/utils/projectGraphs.ts` |
| how long tickets take and what they cost — per ticket, per project, across projects; where verification time goes; whole-suite vs filtered runs; orchestrator overhead | `apps/jticket` | the project's **Analytics** tab (`GET /api/projects/:id/analytics`) and the global **Analytics** page (`/analytics`, `GET /api/analytics?repo=&from=&to=&rows=1`), measured entirely passively: every dispatch runs claude with `--session-id` and records the session in the ledger `.data/jticket/sessions.json` (`server/utils/sessions.ts`); `ticket.pickedUpAt` is stamped once on dispatch/claim; the reader parses the session's transcript under `~/.claude/projects/<cwd-slug>/` (`server/utils/transcripts.ts`: usage per message id, tool calls with durations, subagents attributed to tickets by their prompt) into `server/utils/sessionMetrics.ts` (duration, research → first edit, PR opened, cost at list price from `server/utils/pricing.ts`, verification runs classified by `server/utils/verification.ts`: category test/e2e/lint/typecheck/guards/build, scope whole/filtered/single — a codebase adds its own patterns in Codebase settings → Verification rules, `PATCH /api/repos?path= {verificationRules}`); `server/utils/analytics.ts` + `analyticsRollup.ts` roll rows up (orchestrations are measured whole AND per inner ticket). `GET /api/tickets/:id/sessions` is one ticket's row (the modal's timeline strip). **Backfill** (`POST /api/analytics/backfill {project?}`, or the tab's button → `POST /api/projects/:id/analytics/backfill`) matches older transcripts to tickets by their first prompt. Agents report nothing |
| improve/deepen a codebase's architecture | `apps/jticket` | the Improve-architecture button on the projects page (or `POST /api/projects/architect`) makes an architect-mode project whose scan (`/jarchitect-scan`) fills the board with graded HITL candidates + an assessment spec; a candidate's herdr button dispatches its go/no-go grilling (`/jarchitect-grill`, answered in that herdr pane) and finishes the ticket |
| worktrees — how a codebase makes/sets up/runs/tears down worktrees, connecting an integration branch to one | `apps/jticket` | Codebase settings (`/codebase`) → Worktrees: the kickoff button dispatches the `worktree:kickoff` prompt into herdr; the agent asks the codebase (and the human, in its pane), proves the recipe, and PUTs the **worktree guide** to `/api/repos/worktree?repo=`. Every worktree consumer (`/jimplement`, `/jreproduce`, jReview, the connect prompt, the merge sweep) GETs the guide first. Agents take the guide's cheapest form that fits the ticket (a slim/test-only worktree when it has one) and tear worktrees down as soon as the PR is open; the merge sweep removes any worktree still holding a merged head branch (`POST /api/prs/:id/merge` answers `headWorktree`) and deletes the branch, and jReview's watcher removes its reviewer checkouts once a review's panes close. The integration branch's Connect worktree button dispatches `worktree:connect`, which POSTs the link to `/api/projects/:id/worktree` (re-checked against `git worktree list`). Codebase settings also hold the codebase's prompt overrides (ticket → project → codebase → global → built-in) |
| reproduce suspected bugs before a deploy | `apps/jticket` | a predeploy-mode project — one suspected bug per ticket; the herdr button dispatches `/jreproduce`, which reproduces it in a throwaway worktree as a failing test, records the test + verdict (reproduced / flaky / not-reproduced / already-fixed / invalid) on the ticket, and never fixes it |
| charts embedded in articles | shared pool | `packages/charting` serves `/api/charts` over `.data/jchart/` in every consumer — jExplain charts ARE jChart charts |
| block documents (docs, specs, explainers) | shared pool | `packages/documents` serves `/api/documents` over `.data/jexplain/` in jTicket, jExplain AND jGrilling — a jTicket doc IS a jExplain document |
| dispatching terminal claude sessions into herdr | shared pool | `packages/herdr` (`ensureHerdrWorkspace`, `acquirePackedPane`, `startClaudeIn`) — jTicket, jDiff, jCode and jReview dispatch through it (jMap's phases are dispatched by jTicket; jDiff's sessions run the `jdiff-review`/`jdiff-ask`/`jdiff-tour`/`jdiff-chains` skills on Opus 5; jCode dispatches `jcode-mark`; jReview its reviewers, triage and consensus sessions); jTicket's Run-review buttons proxy to jDiff's dispatch with ticket/project context, and the review session reports findings back into jTicket (fix tickets / ticket comments) |
| sync/share a jTicket project with a coworker's machine | `apps/jticket` | the project page's Share panel — pull-only snapshot sync over Supabase Realtime Broadcast (frames sealed end-to-end with the share's room secret), 2-hour capability links, every pull approved in the serving side's UI; peer-owned entities are read-only and never dispatchable. One-time setup: `packages/relay/wizard.sh` (creates/wires a free Supabase project); both machines wire the same project into `.data/jticket/sync.json` (`JTICKET_SUPABASE_URL`/`_KEY` override). See README "@jsuite/relay" |

When a request spans apps (e.g. "spec this, then diagram it"), do each part with
that app's own skill rather than improvising one app's job in another.

## Rules of the suite

- **State lives in `.data/<app>/` at this root, never inside an app.** Use
  `@jsuite/data` (`appDataDir`/`appDataFile`) to resolve paths. jTicket's state
  is API-only — go through :43000, don't hand-edit `.data/jticket/jticket.json`.
- **URLs always carry the scheme**: `https://<app>.local`. Bare host ports
  (43000–43008) work too but the `.local` names are what tooling hardcodes.
- **Ports are fixed.** The `APPS` table in `./jsuite`, the `Caddyfile`, and
  skills that hardcode ports (to-jticket → :43000) must stay in sync.
- **Adding an app**: follow "Adding an app" in `README.md` — `apps/<id>`, `APPS`
  row, `Caddyfile` block, `DOMAINS` entry + the `dev.orbstack.domains` label in
  `docker-compose.yml`, allowlist the `.local` name in
  `vite.server.allowedHosts`, then `./jsuite restart`. Also add a card to
  `www/index.html` and update the `jsuite` skill's app table.
- **Skills are app-owned** in `<app>/.claude/skills`; the suite-level `jsuite`
  skill lives in `.claude/skills/` here at the root. `./jsuite setup` installs
  all of them globally from `SKILLS_MANIFEST` in `./jsuite` — new skill ⇒ new
  manifest entry (and keep `apps/jticket/j-setup` in sync for jticket-owned
  ones).
- **One git repo covers the whole workspace.** Apps no longer carry their own
  `.git`; commit everything (apps, packages, skills) from this root.
- **Don't restart apps blindly.** `./jsuite status` first; `./jsuite start` is
  idempotent for already-running apps but refuses ports held by processes it
  didn't start. Logs are at `logs/<app>.log` (`./jsuite logs <app>`).

## Layout

```
jsuite            # launcher: start/stop/status/logs/open/setup
                  # (setup also installs every jskill globally — SKILLS_MANIFEST)
Caddyfile         # edge config — one block per .local name
www/index.html    # static ecosystem index at https://jsuite.local
.claude/skills/   # suite-level skills (jsuite)
apps/             # jticket jdiff jchart jexplain jgrilling jcode jmap jreview
packages/         # @jsuite/charting + @jsuite/documents (Nuxt layers), @jsuite/data (.data resolver), @jsuite/herdr (herdr dispatch adapter), @jsuite/relay (sync setup wizard + local broadcast relay)
.data/<app>/      # ALL app state, gitignored
```
