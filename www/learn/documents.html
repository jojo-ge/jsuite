Why it exists

When you ask Claude to explain a system, a PR or a decision, the answer usually arrives as chat: unstructured, unshareable, gone when the session ends. A document publishes it as an article. Each part is a typed block, so code gets syntax highlighting, diffs get proper diff rendering, key terms get a glossary, and warnings get callouts.

Reading is only half the loop. Pin a note to any block (a question, a correction, a “go deeper here”) and “Copy notes for Claude” bundles all your feedback into one payload for the next revision.

The explainer loop

  1. Ask for an explainer. The j-explain skill structures the answer into typed blocks and publishes it with explain.py.
  2. Read it as an article. It opens in jTicket's reader at /e/<key>, with real typography, rendered code and diffs, and live charts.
  3. Annotate blocks. Pin notes to exactly the paragraphs or code blocks that need work.
  4. Send notes back. “Copy notes for Claude” hands your feedback to the next session; a --replace publish revises the article in place.

Skills that drive it

j-explain

Explains a concept, a PR, a system or a decision as an article. It owns the explain.py publish script and the block vocabulary every other document skill uses.

to-jdoc

Writes a spec, a design note or any page into a project as a doc, for review locally first, and says which field renders what. Nothing is posted to Confluence.

One pool, one set of charts

A project's doc in jTicket wraps a document in the pool with project, status and label metadata, so the doc on the board and the article in the reader are the same object. Figures aren't screenshots either: a chart block embeds a chart from the shared chart pool, so fixing a label in the chart editor fixes the article.
