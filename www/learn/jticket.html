jTicket — the planning hub

Projects, epics and tickets with acceptance criteria and blocked-by edges, plus Confluence-style draft docs. Deliberately not connected to Jira or Confluence — breakdowns and specs land locally first, for you to review before anything goes upstream.

Why it exists

When Claude breaks a plan into work, the natural failure mode is a wall of chat text you skim once and lose. jTicket gives that breakdown a real board: epics containing tickets, each with acceptance criteria and blocked-by edges, that you can inspect, reorder, edit and veto — before any of it is copied into a real tracker.

The same applies to documents. Specs, design notes and RFCs are drafted as Confluence-style docs inside jTicket — panels, expand sections, tables of contents, status lozenges — so you review the finished page locally instead of discovering problems after it's published.

How a plan becomes a board

  1. Plan in conversation. You and Claude settle on what to build, in whatever session that happens.
  2. Break it down. The to-jticket skill turns the plan into a project with epics and tickets over the HTTP API — acceptance criteria and blocking edges included.
  3. Review on the board. Open the app, drag things around, tighten criteria, delete what's wrong.
  4. Implement from it. jimplement claims a ticket, builds it, and records the outcome back on the board — so the board stays the source of truth for what happened.

Skills that drive it

Everything goes through the HTTP API on :3000 — the state file is never hand-edited, so every skill and every session sees the same board.

to-jticket

The general interface: break a plan into tickets, author or update any project, epic, ticket, doc or attachment, and query the board.

to-jspec

Write a spec into jTicket as a doc, using the jdoc markdown dialect — panels, expand, toc, status lozenges, mentions — with the exact publish call. Used whenever any doc body or ticket description is being authored.

to-jdoc

Draft a Confluence-style page into jTicket without posting anything to Confluence — for design notes, RFCs, or any page you want reviewed locally first.

jwayfinder

Plan a chunk of work too big for one agent session: it becomes a shared map of investigation tickets, resolved one at a time until the way to the destination is clear.

jimplement

Implement work already broken down as tickets — claim a ticket, build it, and record the outcome back on the board.

State & integration

State
.data/jticket/jticket.json + attachments/ — but API-only: always go through :3000, never edit the file.
Upstream
None. jTicket is a local staging ground; copying approved work into Jira/Confluence is a separate, deliberate step.
Suite role
The planning end of the loop — jDiff reviews what jimplement built; jExplain writes up what shipped.
