Reviews & diffs — several reviewers, one diff viewer

A review sends several Claude reviewers at a branch and keeps only what they agree on, as tickets on a project's board. The Reviews board does the same for someone's GitHub PR. A project's Diff tab is where you read the change yourself, with a guided tour if you want one.

Why it exists

One reviewer is noisy, and you have to weigh every finding yourself. jTicket runs two to four reviewers side by side, each in its own herdr session, and a final session keeps only the findings they agree on. Every review belongs to a project, and its findings land as tickets on that project's board, so nothing gets lost in chat.

Reviewing a GitHub PR

  1. Pick the PR. The Reviews board lists the codebase's open PRs. Press Review this PR.
  2. Start the review. In the project's Review tab, pick two to four reviewers and press Start review. The PR's head is fetched fresh and every reviewer reads its diff.
  3. Agree and verify. The reviewers report; a consensus session keeps what every reviewer raised, verifies each finding adversarially, and judges whether the PR is approvable, with a summary written to the PR's author. Each finding becomes a ticket on the review's project.
  4. Post on your say-so. Post to PR sends the summary and the finding tickets you pick as one comment review under your own gh login. It never approves and never requests changes. Rerun review runs again on the PR's new head.

The Diff tab and tours

Every project has a Diff tab: a side-by-side diff of the integration branch, a local PR, a GitHub PR or any two refs, computed locally by git, with expandable context and a full-file view. Build tour dispatches a claude session that walks the change stop by stop. Tours are for you; reviewers never see them.

Skills that drive it

jreview-consensus

Keeps only the findings every reviewer raised and verifies each one.

jdiff-tour

Builds the guided tour of a change for the Diff tab.
